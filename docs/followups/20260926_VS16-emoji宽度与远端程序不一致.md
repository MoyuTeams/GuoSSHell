# 带 VS16 的 emoji 宽度与远端程序不一致

- 状态：待决定（兼容性取舍）
- 记录日期：2026-09-26

## 问题

默认按文本呈现的字符后接 VS16（U+FE0F）构成 emoji 呈现序列，如 ⚠️、✔️、❤️。引擎
（alacritty_terminal）按码点计宽：基字符 1 列、VS16 0 列，整体 1 列，并按文本样式画成单色字形。
opencode（opentui）按 Unicode 的 emoji 规范算 2 列，kitty、WezTerm、Ghostty 等终端也是 2 列。

两边差一列，opencode 画出的行在这类 emoji 之后与引擎错开一格：

- emoji 后面多出一格空白（opencode 以为那是 emoji 的后半格，不写）；
- 这一格原来有字时旧字符留着——重绘表格时出现「⚠-」这样的残留。

反过来，按 C 库 `wcwidth` 计宽的程序（bash / readline、vim 等）也把它算作 1 列，与引擎一致；
所以改成 2 列会让这些程序错位。

## 现状

- M6 验收（docs/acceptance-m6-2026-09-26.md §8）的 opencode 截图中可见：列表项「⚠️」后多一格空白。
  画面一致性自检不报（引擎与 Dart 一致，差异在引擎与远端程序之间）。
- 同类问题：ZWJ 序列（👨‍👩‍👧）、肤色修饰（👍🏽）、旗帜（🇨🇳）在引擎里按码点分别计宽，与按字素计宽的
  程序也不一致；agent 的剧本没有覆盖它们。
- 真机的 `m6-cjk` 截图同样可见家族、肤色和旗帜序列被拆开显示。逐列一致性断言通过并不代表这些
  字素簇已经正确合成为一个图形；这部分仍需独立视觉验收。

## 下一步

1. 决定引擎的计宽规则：维持按码点（与 `wcwidth` 一致），或 emoji 呈现序列按 2 列
   （与 opencode、新一代终端一致），或支持字素簇模式（DECSET 2027）由远端程序协商。
2. 选定后的实现在 rsHell / alacritty_terminal 的输入路径（VS16 到来时把前一格改成宽字符并前移光标，
   或按字素簇计宽）；emoji 呈现的格 Dart 画彩色字形（现在是单色）。M6 的 `m6-cjk` 图样与 opencode
   用例守住。
