# Scoped 压缩的工作区与有界执行

## 问题与现状

风险等级：中，不可信压缩流可能造成 CPU／内存压力。第三方 workspace、内部有界推进及秘密字典完整清理延至本分支之后；本分支使用正常压缩入口，落实应用输出、队列和并发控制，实际响应性缺陷仍须修复。新 codec 不作为桌面交付前件。

正常 scoped 网络尚未完成压缩资源闭包。当前 KEX 会宣告压缩算法，但 scoped 认证成功路径对非 `none` 协商结果返回 `PolicyUnavailable`；这不满足正常 `zlib`、`zlib@openssh.com` 的连接要求。旧 Native 压缩路径保持原行为。

SDK 独立候选构建图中的 `flate2 1.1.9` 使用 `miniz_oxide 0.8.9` Rust 后端；应用当前实际图为 `flate2 1.1.10`／`miniz_oxide 0.9.1`。两者的源图证据不能互代，fork 来源和固定身份仅记录在根 `UPSTREAM.md`。已核对的候选后端会在构造压缩／解压状态时创建库私有 Box，压缩状态还持有外置字典、哈希和编码缓冲；russh 的输出 Vec 也会增长。公开接口没有调用方工作区或 scoped 分配入口，外层 root 的擦除不覆盖内部 Box。尚无内部秘密缓冲在实际 dealloc 前完整擦除的证明。

现有 cooperative 预算只限制外层 poll，不能据此证明同步压缩调用和扩容循环的工作量有界。解压输出长度上限也不代替分配前准入或 CPU 进展证据。

## 分支后下一步与验收条件

- 明确依赖层最小接缝的实施范围，使状态及内部工作区可由调用方实际拥有，支持调用前 source-derived grant、分配失败、完整秘密擦除及最后 backing/header 释放后退款。不得用外层估算预约、复制第三方源码或关闭正常压缩来签收。
- 将输入、输出增长和压缩计算接入 rooted owner 与可恢复的有界执行；取消和 rekey/reset 保留真实持有者直到清理完成。
- 用真实 SSH 对端验证两种 zlib 协商、双向数据、rekey、拒额／NULL、取消及另一连接持续进展，并审计全部状态和输出分配的源式、擦除与释放顺序。
- 非 Windows 目标和完整网络／P1 验收仍须取得各自实际证据；本条目不代表压缩接缝已实现或正常网络可开放。
